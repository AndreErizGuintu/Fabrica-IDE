  **CORRECTION [2026-08-08, later same day] — the "model-capability limit" conclusion above is DISPROVEN. Root cause was a system-prompt DELIVERY bug, not the model and not the wording.** A diagnostic pass traced the delivery mechanism end to end. The `ai:translate` system prompt string was built correctly and passed correctly into `generate()` (`main.ts` → `generate(userPrompt, systemPrompt, cb)`), and `generate()` created a fresh `LlamaChatSession` per call (07-28 pattern intact) — but it passed `systemPrompt` as an option to **`session.prompt()`** instead of to the **`LlamaChatSession` constructor**. Per the installed node-llama-cpp 3.19.0 types: `LlamaChatSessionOptions` (constructor) **has** `systemPrompt?: string`; `LLamaChatPromptOptions` (`.prompt()`) **has no `systemPrompt` field**. So the property was an excess key that node-llama-cpp **silently dropped — the model never received the system prompt on any call.** `tsc` didn't catch it because `LLamaChatPromptOptions` is a union-shaped intersection type, which disables TypeScript's excess-property checking. **All three "prompt rewrite" attempts were editing a string that never reached the model** — which is exactly why wording changes did nothing while the same GGUF quant, given the identical task through Ollama (which delivers the system prompt as a real `system` role), produced the import correctly. **Fix applied:** moved `systemPrompt` into the `SessionCtor({ contextSequence, systemPrompt })` constructor and removed it from `session.prompt()`'s options (`llm.ts`). `tsc --noEmit` clean. The directive import wording in `main.ts` is left as-is — now that it is actually delivered, it should finally take effect. **Not yet re-tested against the repro — Andre to confirm `import 'dart:math'` now appears for the `Math.min`/`Math.max` → Dart case.**

  **Escalation status DOWNGRADED:** the deterministic post-generation import check (items 1-4 above) is **no longer a planned Aug 13-29 fix — it is now a FALLBACK, only to be built if the now-correctly-delivered system-prompt instruction still proves insufficient after a real test.** The likely outcome is that it is unnecessary. Keep the design notes above for reference; do not build speculatively before the delivery fix is tested.

- **[2026-08-08]** **System-prompt delivery bug in `llm.ts` — affected `ai:translate` AND `ai:explain` identically; `ai:complete` (Ask/Plan) was immune.** Companion entry to the correction above, recording the full blast radius so this isn't mistaken for a Translate-only issue. ## Main-process blocking — investigation findings (dominant cause fixed AND CONFIRMED 08-09; migration still open, see §8)

**[2026-08-07]** Scoping pass only — **nothing implemented, no code touched.** Follows up the 08-07 `@electron/llm` reference entry above (item 4), which named the utility process as the root-cause fix but did not scope it. This section is that scope. The bug being scoped: during any `generate()` call the whole app becomes unresponsive/unclickable — directly observed during Code Inference testing, but Code Inference is not special. All five AI entry points (`ai:complete`, `ai:translate`, `ai:explain`, `adaptive:hint`, `codeInference:request`) funnel through the same `generate()` in `src/main/llm.ts`, so every one of them freezes the app for the duration of its generation.

**Naming correction up front:** the env var is `GGML_VK_VISIBLE_DEVICES`, not `GPU_VK_VISIBLE_DEVICES`. Recorded so a future grep for the wrong name doesn't come back empty and get read as "the isolation code is gone."

### 1. Is `utilityProcess` actually available? — Yes, no upgrade needed

- Electron **`^35.0.2`** (`package.json` devDependencies). `utilityProcess.fork()` landed in Electron 22, so it has been available this whole time. No version bump, no migration prerequisite.
- `node-llama-cpp` **3.19.0**, in root `dependencies` (not `release/app`). Already webpack-externalized by name in `.erb/configs/webpack.config.base.ts:11` (`externals: [...Object.keys(externals || {}), 'node-llama-cpp']`), so a new worker bundle inherits the externalization for free — no build-config work on that axis.
- **Native-ABI risk is lower than it looks.** `node-llama-cpp` is already proven to load outside the main process today: `gpuIsolation.ts:74-81` runs it via `execFile(process.execPath, ['-e', probeScript], { ELECTRON_RUN_AS_NODE: '1' })` on every packaged cold start. A utility process is the same Electron Node ABI as both of those, so the prebuilt binary question is already answered in the affirmative. The dynamic-`import()`-via-`new Function` shim at `llm.ts:49-53` (needed because the bundle is CJS and the package is ESM) carries over unchanged.

### 2. What is actually coupled to the main process? — Almost nothing. One line.

`llm.ts` is 346 lines and **exactly one thing in it requires Electron's main process**: `import { app } from 'electron'` (line 3), used only by `getModelPath()` (lines 55-65) for `app.isPackaged` and `app.getAppPath()`. Everything else — the `modelConfig.json` import, `fs`/`path`, the `GPU_LAYERS` env read, the `loadModelWithFallback()` step-down ladder, the single-flight lock, `AbortController` — is plain Node and moves as-is.

Fix for that one coupling: **main resolves the model path and hands it to the worker** (fork arg or env), so the worker never imports `electron` at all. ~10 lines. Design it this way rather than testing whether `app` happens to be reachable inside a utility process — the utility process only guarantees a Node environment plus `process.parentPort`, and depending on main-process module availability there would be building on an assumption for no benefit.

**The module boundary is a single function — this is the biggest de-risking finding.** Grepped every export of `llm.ts` across `src/` and `scripts/`:

| Export | External callers |
|---|---|
| `generate()` | 5 — `main.ts` (`ai:complete`/`ai:translate`/`ai:explain`/`llama-test-ping`), `adaptiveEngine.ts:363`, `codeInference.ts:400` |
| `initLlama()` | **0** (internal to `llm.ts`) |
| `isModelBusy()` | **0** |
| `ModelBusyError` | **0** — only referenced in comments |
| `GenerationAbortedError` | **0** — only referenced in comments |
| `GPU_LAYERS`, `GenerationPriority` | **0** outside `llm.ts` |

So the port has one real contract to preserve: `generate(prompt, systemPrompt?, onTextChunk?, options?)`. `initLlama()` and the lock can move wholesale into the worker with zero call-site churn.

**What correctly stays in main:** `adaptiveEngine.ts` and `codeInference.ts` both import `stats.ts`, which needs `app.getPath('userData')` (`stats.ts:41`). They are main-process modules and should remain so — they are prompt-building and policy, not inference. The split is clean: policy in main, model in worker.

### 3. GPU isolation — the utility process **helps** here rather than fighting it

This was the part expected to be the blocker. It is closer to the opposite.

Two mechanisms exist today:
- **Dev:** `scripts/resolve-gpu-isolation.mjs` probes GPU names under plain Node *before* Electron exists, then `spawn`s `npm run start:renderer` with `GGML_VK_VISIBLE_DEVICES` injected into the child env (line 98). It inherits down the npm/webpack/electronmon chain into Electron at creation.
- **Packaged:** `ensureGpuDeviceIsolation()` (`gpuIsolation.ts:127-184`), called at `app.whenReady()` before `createWindow()` (`main.ts:817`). Probes, sets `process.env`, then `app.relaunch()` + `app.exit(0)`.

The reason for that relaunch is documented at `gpuIsolation.ts:15-25` and was **confirmed by testing, not theorised**: setting `GGML_VK_VISIBLE_DEVICES` mid-process does not reach the native Vulkan backend. It only takes effect when present in the OS process environment block **from the moment the process is created**.

**`utilityProcess.fork(modulePath, args, { env })` is a process creation with an env block we control.** That is precisely the condition the var requires. Consequences:

- **Inheritance works by default.** A forked worker inherits main's `process.env`. In dev the var is already set before Electron launched, so a worker forked from main gets the correct value with **zero changes to either isolation mechanism**.
- **Explicit is better.** Main should pass `env: { ...process.env, GGML_VK_VISIBLE_DEVICES: String(idx) }` on the fork. Doing so makes the entire mid-process-mutation problem vanish for the inference process, because the fork *is* the creation moment.
- **Therefore the `app.relaunch()` + `app.exit(0)` dance becomes unnecessary in principle** — probe once at startup, hand the resolved index to the fork, never restart the app. That is a genuine simplification the migration unlocks, not merely a thing it survives.
- **But do NOT bundle that simplification into the same change.** The relaunch path is currently the only isolation route verified working on packaged builds, and it interacts with the loop-guard at `gpuIsolation.ts:140` (`if (process.env.GGML_VK_VISIBLE_DEVICES) return`) that is also the only thing preventing a relaunch loop. Port first, keep the relaunch, remove it as a separate independently-testable follow-up.
- **One thing to verify empirically rather than assume:** the "present at creation" constraint was established for the Electron *main* process specifically. Confirm a forked worker genuinely sees one device. **The diagnostic for this already exists** — `llm.ts:129-130` logs `getGpuDeviceNames()` and `getVramState()` immediately after `getLlama()`. Reuse those two lines inside the worker; do not write a new probe.
- The probe itself (`execFile` + `ELECTRON_RUN_AS_NODE`) stays in main, untouched.

### 4. IPC surface — yes, this can be an internal implementation detail

**No renderer-visible change is required, and none should be made.** Zero edits to `preload.ts`, `preload.d.ts`, or any renderer file. `ai:token`, `adaptive:hint`, `codeInference:request`, `codeInference:checkTrigger`, `ai:complete`/`translate`/`explain` all keep their exact current contracts.

Shape: `llm.ts` keeps its current signature and becomes a thin proxy — ensure worker alive → post a request with an id → return a promise. Token chunks arrive on the MessagePort and are re-dispatched into the caller's `onTextChunk` callback, which is where the existing `event.sender.send('ai:token', chunk)` calls already sit (`main.ts:832`, `855`, `877`). Those lines do not change.

Costs and sharp edges of the extra hop:
- **Streaming becomes worker → main → renderer, two hops per token instead of one.** At 6.7B-on-6GB token rates the added latency is noise, but it is worth stating honestly that main is no longer *blocked* yet also not at *zero* cost per token. The win is real; it is not literally free.
- **`AbortSignal` is not structured-cloneable.** `options.signal` cannot cross the port and must be flattened into a `cancel(id)` message. **Currently no caller passes `signal`** (verified — `adaptiveEngine.ts:363` and `codeInference.ts:400` pass only `maxTokens`/`contextSize`/`priority`/`stopTriggers`), so this is a forward-looking cost, not an immediate breakage. It is also the thing that makes 08-07 item 1 (cancellation) genuinely reachable afterwards.
- **Error identity does not survive `postMessage` automatically.** A thrown `Error` subclass arrives as a plain object. Both existing catch sites read `(err as Error).name`/`.message` (`codeInference.ts:421`) rather than using `instanceof`, so name-based reconstruction is sufficient — but it has to be deliberate serialize/rehydrate, not an accident.
- **One design decision to make, not a mechanical one: where the single-flight lock lives** (`llm.ts:193-345`). Recommend **inside the worker** — one owner of the model, one owner of its lock. Keeping it in main would preserve `isModelBusy()` accuracy for free, but that export has zero callers, so there is nothing to preserve. Worker-side is the cleaner invariant.

### 5. Effort and risk — a full dedicated session plus its own test pass

Not a one-liner; not a rewrite either. **Comparable in scope to the Adaptive Engine MVP or the Code Inference build** — one full session for the port, and realistically a second shorter pass for packaged-build/GPU verification. Risk: **medium.** Nothing is architecturally blocked. The cost is surface area, and one genuinely new failure mode.

Concrete work items:
1. **New webpack entry (`llmWorker`) in BOTH main configs.** Dev (`webpack.config.main.dev.ts:26`) emits to `webpackPaths.dllPath` as `[name].bundle.dev.js`; prod (`webpack.config.main.prod.ts`) emits to `distMainPath` as `[name].js`. **Different directory AND different filename**, so the fork-path resolver needs a dev/packaged branch — same shape as `getModelPath()`'s existing `app.isPackaged` branch. **This is the single most likely item to eat an unplanned hour:** it is build config, and it fails at runtime with a module-not-found, not at compile time.
2. Split `llm.ts` → `llmWorker.ts` (model load + ladder + lock + generation, talking over `process.parentPort`) and `llm.ts` (proxy preserving the `generate()` signature).
3. Move model-path resolution into main; pass the resolved absolute path to the worker.
4. Define the message protocol: request id, `token`, `done`, `error`, `cancel`.
5. **Worker lifecycle** — lazy spawn on first `generate()`, `exit` handler, respawn-on-crash policy, teardown hooked into the existing `app.on('before-quit')` (`main.ts:798`).
6. Error/abort serialization (see §4).
7. **`electronmon` hot-reload check (dev-loop regression risk).** Dev restarts main on every change. A forked worker holding a loaded 6.7B model must actually die on reload, or VRAM leaks across hot reloads until the machine runs out — which on a 6GB card is a handful of reloads, and would present as spurious `ErrorOutOfDeviceMemory`.

Afterwards it silently kills only the worker, and every subsequent `generate()` must fail cleanly instead of hanging forever on a promise that will never settle. That failure mode does not exist today and needs deliberate handling in item 5 — it is the most likely way this migration produces a *worse* demo experience than the freeze it fixes.

**Sequencing:** do not combine this with the `app.relaunch()` removal (§3) or with 08-07 item 2 (context/session reuse) — that would be three interacting changes to the same file in one pass, one of which (context reuse) pulls directly against the 07-28 conversation-bleed fix. ### 6. Interim mitigation — one cheap real option, and one non-option worth naming

**Structural point that kills the obvious idea first:** a renderer-side "Cancel"/"Stop" button **cannot work as an interim fix.** If main's event loop is blocked, it cannot receive the cancel IPC. Cancellation is not a mitigation available before the utility process — it is something the utility process *unlocks*. Worth recording so it doesn't get attempted and debugged as if it were broken.

Worth doing now:

- **(a) Measure before committing — highest value, ~30 minutes.** Add a main-process event-loop lag probe (a `setInterval` recording timer drift) and log it across a `generate()`. - **(b) Cap inference threads — one line, actions a flag already open since 07-24.** Verified present in the installed 3.19.0: `maxThreads` on `getLlama()` options (`node_modules/node-llama-cpp/dist/bindings/getLlama.d.ts:105`) and `threads` on context options. **Both are currently unset** — `llm.ts:124` calls `getLlama()` with no arguments and `llm.ts:296-298` passes only `contextSize`. Capping to roughly cores−2 costs some tok/s and may measurably soften the freeze. This also finally actions the deferred **2026-07-24 "CPU thread count tuning"** flag. **Still not a fix:** a blocking native call blocks regardless of thread count — which is exactly what (a) tells you.

Hold unless (a) says the utility process won't help:

- **(c) Warm the model outside the first user action.** Today the first `generate()` pays model load + `loadModelWithFallback()`'s probe-context validation + generation as one unbroken block — the worst single freeze in the app. Calling `initLlama()` at startup or on project open doesn't make main non-blocking, but it relocates that stall to a moment where a wait is already expected instead of onto the student's first Ask.

Purely cosmetic, but it converts "the app crashed" into "the app is thinking," which is the actual defense-demo risk. `src/renderer/components/` is teammate-owned — **relay, don't edit.**
- **(e) `maxTokens` is a freeze-duration dial.** Fewer tokens = shorter block. Note the interaction with the 08-07 flag about `maxTokens: 48` being too low for post-pivot Code Inference: raising it to fix truncation **lengthens the freeze proportionally**. ### 8. §7's `createContext()` attribution corrected — real culprit found, measured, and fixed [2026-08-09]

**§7's verdict that the 7566ms stall is `await model.createContext()` does not hold. It was a log-position guess, and it was wrong.** §2 of this same section (untouched, still correct) had already independently proven `createContext()` itself is cheap (~200-460ms) and runs off the JS thread via a native `Napi::AsyncWorker` — so §7 and §2 were in quiet tension the whole time, unresolved until tonight because nothing between `createContext()` and `GENERATION START` was individually timed. It just happened to be the last named call before the gap in the log, so the gap got credited to it.

**What closed the gap: per-phase timing instrumentation added directly to `generate()`'s real path in `llm.ts`** (`process.hrtime.bigint()` around each phase — lock-acquire, `initLlama()`, `getLlama()`, `loadModelWithFallback()`, `createContext()`, `new LlamaChatSession()`, prompt time-to-first-token, prompt total — gated behind the existing `LOCK_DEBUG` flag, logged as `[generate:phase] ...`, each line also carrying `Date.now()` start/end so it lines up directly against `[heartbeat]`'s own timestamps). Andre ran the real app with both `HEARTBEAT_DEBUG=1` and `LOCK_DEBUG` on and captured three real generations to `session.log`.

**Result, reproduced 3/3, warm and cold:**

| Gen | `new LlamaChatSession()` phase duration | Heartbeat gap immediately after | 
|---|---|---|
| #1 (cold) | 3081.0ms | 3116ms |
| #2 (warm) | 2902.7ms | 2918ms |
| #3 (warm) | 2974.9ms | 2985ms |

**Root cause, traced through the actual node-llama-cpp source:** `new LlamaChatSession()` → `new LlamaChat({ chatWrapper: "auto", ... })` → `LlamaChat`'s constructor runs `this._chatWrapper = chatWrapper === "auto" ? resolveChatWrapper(contextSequence.model) : chatWrapper` **synchronously, no `await` anywhere in the chain** (`node_modules/node-llama-cpp/dist/evaluator/LlamaChat/LlamaChat.js:53-55`). Because this GGUF carries `tokenizer.chat_template` metadata (the same jinja-template presence already noted for the `special_eos_id` gap, 08-04 entry above), `resolveChatWrapper()` lands in its most expensive branch (`resolveChatWrapper.js:127-190`): for **all 16 built-in specialized wrapper types**, for up to 4 settings variants each, it constructs a real `JinjaTemplateChatWrapper` (compiles the model's actual Jinja template) and calls `isJinjaTemplateEquivalentToSpecializedChatWrapper()`, which **actually renders** the compiled template against a battery of canned test chat histories and string/token-compares the output against each candidate wrapper. None of the 16 candidates matched this model (confirmed empirically below), so it falls through every one of them before landing on a fresh `JinjaTemplateChatWrapper` as the final answer — the worst-case, most expensive path through the function.

**Standalone confirmation** (`gpuLayers: 20`, isolated Vulkan device, same model): three consecutive `resolveChatWrapper(model)` calls all returned a `JinjaTemplateChatWrapper` with byte-identical `.settings` (`JSON.stringify` equal all three ways) — deterministic, model-only, no per-call variance. A single isolated call cost **2781.1ms** — on its own, close to the entire measured freeze, confirming this function (not something incidental nearby) is the mechanism.

**Fix implemented in `llm.ts` — resolve once, reuse:** `initLlama()` now calls `resolveChatWrapper(model)` once (right after `loadModelWithFallback()` resolves the model, timed via the same `phaseLog` pattern as its siblings) and returns it alongside `{ llama, model }` in `LlamaRuntime`. `generate()` destructures `chatWrapper` from `initLlama()` and passes it explicitly into `new SessionCtor({ ..., chatWrapper, systemPrompt })` instead of leaving the option unset (which defaults to `"auto"` and re-triggers the full 16×4 search every call). `resolveChatWrapper` is a first-class public export of `node-llama-cpp` (`index.js`) — no reimplementation, just import and use.

**Why this is safe and does not interact with the 07-28 fresh-session-per-call fix:** that fix addressed conversation *history* bleeding across calls (each `generate()` gets a brand-new, empty-history session). `chatWrapper` carries zero conversation state — it is pure, stateless formatting logic ("how does this model's chat template lay out system/user/model turns"), resolved once from the model's static GGUF metadata and provably identical every time for a given loaded model (confirmed above). A fresh, empty-history session built with a *cached* wrapper is byte-for-byte behaviorally identical to one that re-resolves `"auto"` from scratch — there is nothing here that can leak between calls. No changes to locking, context lifecycle, or session freshness.

**Verification status: CONFIRMED end-to-end in the real Electron app** (not just the standalone script) — Andre ran the app with `HEARTBEAT_DEBUG=1` and `LOCK_DEBUG` on, captured three real generations to `session.log`. Investigation chain complete: heartbeat probe → phase instrumentation → source tracing → caching fix → confirmation run.

### [2026-08-10] §9 — Utility-process migration follow-up: `stdio: 'inherit'` silently swallowed 100% of worker log output. Fixed with an explicit JS relay.

**Symptom.** The first post-migration test run produced a `session.log` in which a generation completed **successfully end-to-end** (worker forked, `ready` handshake done, AI panel returned real text) while printing **zero** lines from `llmWorker.ts`. No `[llm] DIAGNOSTIC: process.env.GGML_VK_VISIBLE_DEVICES...`, no `getGpuDeviceNames()` / `getVramState()`, no `[llm] Model loaded successfully with gpuLayers=`, no `[generate:phase]`, no `[CodeInference:lock] ... generate() ENTRY`. Every diagnostic §7-§8 was built on had gone dark in one move.

**Why the log could not diagnose itself.** The only two `[llm]` lines present (`forking inference utility process`, `inference utility process ready (pid 22956)`) are printed by **main**, not the worker — and `llmWorker.ts` printed nothing at all before `post({ type: 'ready' })`. So the log contained no evidence either way about whether worker output reaches the terminal, which left "worker never got the request" and "worker output is being dropped" indistinguishable. The successful generation is what settled it: the worker demonstrably ran, so the output was being dropped.

**Root cause.** `spawnWorker()` passed `stdio: 'inherit'` (also Electron's default), on the assumption that a utility process inherits main's stdout the way a `child_process.fork()` child would. It does not — a utility process is a **Chromium child process launched through Chromium's process launcher**, so 'inherit' depends on the browser process's OS-level stdout/stderr handles surviving that launch. In dev they don't, and main's fd 1 is not a console in the first place: `concurrently` pipes electronmon's stdout (that pipe is the source of the `[1] ` prefix on every line in `session.log`), and electronmon hands its own fds down to electron (`electronmon.js:63-70` — `isStdWritable(process.stdout)` is true, so electron is spawned with `'inherit'`). By the time the utility process launches, the handle it would need to inherit is a pipe owned two processes upstream. Note this is specifically an inheritance failure, not a `concurrently` problem — main's own logs traverse that identical chain fine.

**Fix (`llm.ts`).** Fork with `stdio: 'pipe'` and relay `child.stdout` / `child.stderr` into `process.stdout` / `process.stderr` in JS. This is the same fallback **electronmon itself** uses when it cannot rely on inheritance (`electronmon.js:85-87`, `app.stdout.pipe(stdio[1], { end: false })`), and being a userland relay it is independent of platform and of the Chromium-launcher detail above. Three properties worth keeping if this is ever touched:
- **Raw chunk passthrough** — `sink.write(chunk)` with no line splitting, no added prefix, no re-encoding, so the log prefixes stay byte-identical and existing captures/greps keep working. Line prefixing stays concurrently's job.
- **Attached synchronously on the line after `fork()`**, before any `await`. A readable with no `'data'` listener is paused and *buffers* rather than discards, so no boot-time output can be lost.
- **`'error'` handlers that deliberately swallow.** These fire when the pipe tears down mid-write (worker killed, Ctrl-C); an unhandled stream `'error'` would take main down over lost debug output. A dead log pipe must never be fatal.

**Fix (`llmWorker.ts`).** Added a two-line boot diagnostic (stdout **and** stderr, since `llm.ts` relays them separately) as the first statement after the imports. It exists purely so this failure can never again be invisible: if the worker's logs are broken, the boot line is missing, and that is unambiguous on its own — no inference from later lines required. It sits after the imports rather than above them because webpack hoists ESM imports above all other statements regardless of source order; every import above it is side-effect-free and `node-llama-cpp` is loaded lazily, so nothing heavy runs first. Also corrected the file's header comment, which had asserted 'inherit' meant these lines "still land in the same dev terminal they always did."

`tsc --noEmit` clean. **VERIFIED 2026-08-10 on a real run** (3 explicit generations, `HEARTBEAT_DEBUG=1`): both BOOT lines present (so both relays work), and the complete pre-migration diagnostic set is back — `[llm] DIAGNOSTIC:` ×3, all `[generate:phase]` lines, all `[CodeInference:lock]` lines, plus node-llama-cpp's own native load warnings (`control-looking token`, `special_eos_id is not in special_eog_ids`), confirming the relay carries the native layer's output too and not just JS `console.*`.

### [2026-08-10] §10 — Utility-process migration PART 2: worker lifecycle, prod webpack entry, hot-reload teardown. Written, NOT yet run.

**The finding that made item 2 simple: electronmon's hot-reload restart is already a graceful `app.quit()`.** The worry going in was that electronmon hard-kills main on every save, leaving no chance to clean up. It does not. On a main-file change it sends `'reset'` over IPC to the hook it injects with `--require`, and that hook calls `electron.app.quit()` (`node_modules/electronmon/src/hook.js`, `reset()` → `exit(signal)`). So **`before-quit` fires on every dev file save**, and one handler covers both hot-reload teardown (item 2) and normal-quit teardown (item 5). No electronmon-specific hook, no custom signal, no separate code path. `app.on('before-quit')` in `main.ts` now calls `shutdownWorker('app quit')`.

Two constraints that shape that function: it must be **synchronous** (nothing awaits `before-quit`, and electronmon's hook additionally registers a `will-quit` listener that calls `app.exit(37)` immediately after), which is why `llm.ts` keeps a plain `activeWorker` handle alongside `workerPromise` — you cannot await a promise on the way out. And it fails all outstanding requests itself rather than leaving it to the async `'exit'` event, which may never be delivered once main stops running JS.

**Item 3 — crash handling.** `'exit'` now distinguishes intentional kills (a `WeakSet` flag set by `killWorker()`, plus the `shuttingDown` latch) from real crashes, and every exit path settles something. Previously a worker dying mid-request left its caller's promise pending **forever** — the AI panel spinning with no error, no result, no timeout. §5 called this the most likely way the migration ends up worse than the freeze it fixed, and it was: pre-migration a native crash took the app down loudly, which is ugly but unmistakable; a silent hang is strictly worse because nothing downstream can react to it.

**Item 4 — respawn policy: SELF-HEALING, with a crash-loop brake.** A crashed worker is not sticky; `workerPromise` is cleared on exit so the next `generate()` transparently forks a fresh process, with no special-casing at any of the five call sites. Rationale: the crashes worth designing for (native llama.cpp fault, OOM, VRAM exhaustion from another GPU app) are overwhelmingly transient, auto-recovery is exactly what a user would do by hand, and the alternative — a dead AI panel until the whole app restarts — is worse than the pre-migration behaviour. The brake exists because unconditional respawn has a genuinely bad mode: a worker crashing *during model load* (corrupt .gguf, driver fault) would be re-forked on every call at ~14s per attempt. After 3 consecutive crashes with no successful reply in between, `ensureWorker()` refuses and says why. Any reply — `done` **or** a normal `error` response, both of which prove the process is alive and talking — resets the counter. **The threshold of 3 is a judgment call, not a measurement.**

### [2026-08-10] §11 — Utility-process migration PART 3a: real cancellation. Written, NOT yet run. (PART 3b, the `app.relaunch()` retirement, is NOT in this change — see the end.)

**Shape: flatten, don't serialize.** An `AbortSignal` is not structured-cloneable and never will be, so it does not cross the port — that constraint from §4 is unchanged. What changed is that it no longer has to: `llm.ts` keeps accepting `options.signal` on the public `generate()` signature, subscribes to it **main-side**, and turns an abort into a `{ type: 'cancel', id }` message. The signal object stays in main; only the fact that it fired crosses. `WorkerRequest` is now a union of `generate | cancel`, correlated by the same wire id.

**Worker-side registry is separate from the lock, on purpose.** `inFlight` is a single slot describing whichever generation currently holds the model, keyed by nothing. A cancel has to be able to reach a request still **queued behind** that lock — one that has not started and, if the cancel wins, never will. So `llmWorker.ts` keeps `cancellable: Map<wireId, AbortController>`, registered synchronously in `handleGenerateRequest()` and deleted in its `finally`, bracketing exactly the window in which main could still cancel. `runGeneration()` now takes that controller as a parameter instead of creating its own, so both cancellation entry points — a main-side cancel and the lock's existing opportunistic pre-emption — converge on one controller. A new `signal.aborted` check sits immediately after the lock wait and before the slot is claimed, so a request cancelled while queued costs one lock cycle and no work.

**No `cancelled` response type was added, deliberately.** A cancelled generation already has an exact representation: `error` carrying a serialized `GenerationAbortedError`, rehydrated into a real instance main-side, so `instanceof` works at the call site. A fourth response type would mean a second settle path for every consumer to handle for zero information gain. `session.prompt()`'s `signal` + `stopOnAbortSignal: true` were already wired in from the Code Inference build and needed no change.

**ONE SETTLEMENT AUTHORITY — the decision most worth not reversing.** Aborting does **not** settle the promise main-side. It only asks the worker to stop; the promise settles when the worker's reply arrives. Settling locally on abort would be worse in two concrete ways: the worker would keep generating into a promise nobody holds *while still owning the single-flight lock*, blocking the next request for the full remaining generation; and a late `done` for the same id would arrive after the caller had already been told it was cancelled.

Two supporting details: an already-aborted signal is honoured **before** `ensureWorker()`, so an aborted caller cannot trigger a cold fork plus the ~14s model load only to be cancelled on arrival. And settlement now funnels through a single `settlePending()` (plus `failAllPending()`), because each pending entry carries a `cleanup` that detaches its `abort` listener — a caller holding one long-lived signal across many `generate()` calls would otherwise accumulate a listener per call.

**Wiring the 5 existing callers is NOT in this change, and that is a recommendation, not an oversight.** Cancellation is infrastructure here; nothing passes a signal yet. Two callers would genuinely benefit — the three `main.ts` handlers (Ask/Plan, Translate, Explain) want a user-facing Cancel button, and Code Inference wants cancel-on-next-keystroke so a stale ghost-text request stops holding the lock. But both need a new IPC channel (`ai:cancel`), a `window.ai` surface change in `preload.ts`/`preload.d.ts`, and — for the Cancel button — edits to `AIPanel.tsx`, which is **teammate-owned** per CLAUDE.md's ownership boundaries. Bundling a renderer-visible feature into a migration whose whole selling point has been "zero call-site changes, zero renderer-visible change" would also mean this part cannot be tested in isolation. Separate task.

**PART 3b NOT DONE: the `app.relaunch()` GPU-isolation retirement is still open.** §9 confirmed the precondition (a forked worker genuinely sees only the isolated device via plain env inheritance), so it is unblocked — but §3 recorded it should land as "a separate independently-testable follow-up", and shipping an untested GPU-isolation redesign in the same unverified batch as untested cancellation contradicts that directly. Proposed shape, for whenever it is picked up: turn `ensureGpuDeviceIsolation()` into a memoized `resolveIsolatedDeviceIndex(): Promise<string | null>` that probes and classifies exactly as today but **returns** the index instead of relaunching; kick it off non-blocking at startup so the ~40s cold probe stops gating `createWindow()`; have `spawnWorker()` await it and merge the result into the fork's `env`; keep the existing dev fast-path (if `GGML_VK_VISIBLE_DEVICES` is already set by `scripts/resolve-gpu-isolation.mjs`, skip the probe); delete `app.relaunch()` + `app.exit()` and the relaunch loop-guard with them. Net: packaged builds stop double-launching at cold start, and the failure mode if the assumption is wrong is a return of pooled-VRAM overestimation → `ErrorOutOfDeviceMemory`, with the `gpuLayers` step-down ladder as the remaining net.

- **[2026-07-30]** GPU device isolation for hybrid-graphics laptops (RTX 3050 6GB + Intel 
  UHD 770) — root-caused and fixed end-to-end. 

  **Problem:** Vulkan's VRAM reporting pools BOTH devices (dedicated + iGPU shared 
  system RAM) into one combined figure (~13.7-14.7GB) instead of isolating the real 
  per-device VRAM (~6GB on the RTX 3050). This caused gpuLayers: "auto" to badly 
  overestimate available VRAM (resolved to all 33 layers), triggering repeated 
  ggml_vulkan ErrorOutOfDeviceMemory failures on context creation. Confirmed via 
  multiple failed approaches before landing on the real fix: gpuLayers: "auto" alone — 
  fails; gpuLayers: { fitContext: {...} } — fails (still resolves 33 layers off the 
  same bad estimate); GGML_VK_VISIBLE_DEVICES set via mid-process `process.env` 
  mutation inside Electron's main process — silently doesn't take effect (see below).

  **Real root cause (two layers deep):** (1) Vulkan enumeration pools hybrid GPU+iGPU 
  VRAM — a documented upstream issue class, not specific to this codebase (see 
  ollama/ollama#16667, withcatai/node-llama-cpp#413, ggml-org/llama.cpp#18946 for the 
  same failure pattern on other hybrid-GPU laptops). (2) Separately, and specific to 
  Electron: mutating `process.env.GGML_VK_VISIBLE_DEVICES` mid-process, even very early 
  in Electron's main-process lifetime, does NOT propagate to the native ggml-vulkan 
  addon's view of the environment before/during its Vulkan init. Confirmed via a 
  decisive test: setting the var via `cross-env`/shell BEFORE launching Electron (i.e. 
  present in the OS process environment block from process creation) works perfectly 
  on the first attempt — `getVramState()` correctly reports ~6GB, `"auto"` resolves 
  cleanly, zero retries needed. The exact same JS mutation technique worked fine under 
  plain `node.exe` in isolated test scripts — this limitation is specific to mutating 
  env vars inside an already-running Electron process, not general Node/Electron 
  behavior.

  **Fix implemented:** relaunch approach, in `src/main/gpuIsolation.ts`. At app 
  startup (before `createWindow()`), probe GPU devices fresh (via a throwaway child 
  process, to avoid prematurely locking in Vulkan device visibility in the main 
  process), classify dedicated vs. integrated by NAME PATTERN (not index — see 
  verified logic below), and if isolation is needed and `GGML_VK_VISIBLE_DEVICES` 
  isn't already set: set it, then `app.relaunch()` + `app.exit()`. The relaunched OS 
  process inherits the var from creation, so native Vulkan init sees it correctly from 
  the start. Single-GPU/no-GPU machines never trigger a relaunch (probe detects only 
  one device, no-op). Loop-guard: the "already set" check is the natural break — 
  confirmed logged explicitly so a failed guard would be visible, not silent.

  **Classification confirmed robust to enumeration-order instability:** Vulkan's 
  device enumeration ORDER is not guaranteed stable across runs/reboots (observed 
  directly: device index 0 was the RTX 3050 in one manual test, the Intel UHD 770 in 
  another). Verified the real classification logic (not the manual test scripts, which 
  DO blindly trust a hardcoded index and are NOT reliable for this reason) selects by 
  NAME only: `IGPU_NAME_PATTERN = /intel|uhd|iris|graphics/i` combined with 
  `DEDICATED_VENDOR_PATTERN = /nvidia|geforce|rtx|gtx|quadro|amd|radeon/i` — a device 
  is "integrated" only if it matches the iGPU pattern AND does NOT match the dedicated 
  vendor pattern. Walked through both possible enumeration orders explicitly: same GPU 
  selected by name either way, with the index written into the env var changing to 
  match wherever that name actually landed that run. No fixed/assumed index anywhere.

  **Safety net kept:** the step-down retry ladder (gpuLayers "auto" → stepped fixed 
  values → 0/CPU-only on repeated VRAM-pattern errors, with proper model/context 
  dispose() between attempts) stays in llm.ts as a fallback for any machine where even 
  an isolated device's real VRAM estimate still doesn't fit — now a true rarely-used 
  safety net rather than the thing silently doing all the work every launch.

  **Known classification edge cases (not yet hit, flagged for awareness, already 
  commented in code):** AMD iGPU+dGPU laptops — "AMD Radeon(TM) Graphics" (integrated) 
  contains a vendor word, so it isn't excluded by the current pattern, making 
  detection ambiguous (2 candidates) → isolation is correctly skipped rather than 
  guessing wrong, falls through to the retry ladder instead — safe, just not optimal. 
  Intel Arc DEDICATED GPUs would be wrongly excluded as an iGPU by the current "Intel" 
  substring match — unlikely on budget/mid-range student laptops, low priority.

  **Real-world result:** confirmed via actual AI panel use (Ask mode) — generation 
  felt noticeably faster post-fix, consistent with more layers now correctly landing 
  on real GPU memory instead of the retry ladder settling for a lower, scraped-by 
  layer count under the old pooled-VRAM misestimate.

  **Consolidation side-effect (built as a prerequisite for testing this cleanly):** 
  MODEL_FILE is now a single shared source of truth (src/main/modelConfig.json), read 
  by llm.ts, scripts/benchmark.mjs, and scripts/test-gpu-layers.mjs — fixes a 
  duplication pattern that would've silently undermined any future model swap 
  otherwise (same duplication class as the 07-27 runtime-mapping bug).

- **[2026-08-06]** **Code Inference built** — Copilot-style inline ghost-text boilerplate suggestions, as a new isolated capability. Adviser verbally confirmed the concept tonight; official wording pending (see open flag above).

  **Lock added in `llm.ts`:** single-flight `inFlight` slot with a `priority` of `'explicit'` (Ask/Plan/Translate/Explain/Hint — the default, so all four existing callers are unchanged) or `'opportunistic'` (Code Inference only). Explicit **always wins**: it cancels any in-flight opportunistic generation, then proceeds. Two explicit callers now serialize behind each other instead of running concurrently (a behavior change, but strictly safer than the previous unserialized state). - **[2026-08-06]** Code Inference typing-lag bug fixed. Reported symptom: noticeable keystroke lag in fresh `.html`/`.php`/`.cs`/`.dart` files, but smooth in `.js` — correctly isolated to Code Inference.

  **The initial hypothesis (per-keystroke synchronous cost in `provideInlineCompletions`) was wrong, and checking it first is what found the real cause.** On a file bounded to 400 chars, `getValue()` + `trim()` + `getLineCount()` is microseconds. The decisive observation: a fresh `.js` file runs *exactly the same* renderer code and the same IPC round trip — it only diverges inside main, where `shouldTrigger()` returns false because JS has no configured pattern. Since `.js` was smooth, the cost had to be downstream of all the renderer work.

  **Real cause:** only the trigger-eligible path reaches `generate()`, and every attempt calls `model.createContext({ contextSize: 1024 })` then `context.dispose()` — a fresh GPU KV-cache allocation per request, inherited from the 07-28 per-call-context fix — plus inference, all on the Electron **main** process. Main is the browser process that routes input events to the renderer, so occupying it for ~1-3s is felt directly as keystroke lag. In a near-empty file every sub-second typing pause fired a brand-new one.

  **Two real code defects amplified it:**
  1. **A redundant second debounce.** Monaco already debounces before calling the provider. The original `waitForTypingPause()` stacked another 500ms on top, so effective latency was Monaco's adaptive debounce + 500ms, and the provider was still invoked per keystroke. Verified against the real implementation (`monaco-editor@0.55.1`, `inlineCompletionsSource.js:155-162`): it reads `provider.debounceDelayMs`, `await wait(...)` **before** calling the provider, then drops the request if `getVersionId()` changed while waiting. So Monaco already implements exactly the wanted semantics, including stale-request rejection.
  2. **No dedupe and no cooldown.** Every distinct prefix triggered a fresh generation, and typing changes the prefix constantly, so generations chained back to back.

  **Fixes:** (a) deleted the internal debounce, now declares `debounceDelayMs` on the provider so Monaco defers the call itself — provider is no longer invoked per keystroke; (b) reordered guards so `getLineCount()`/`getValueLength()` (both O(1)) run before `getValue()` ever materializes the buffer, which also protects large files that previously paid a full-buffer string build per keystroke just to discover they were too large; (c) single-entry dedupe on `language + prefix + suffix`, caching the null result too so a context that produced nothing is never retried; (d) configurable post-generation cooldown (`cooldownMsAfterGeneration`, default 4000ms) so pauses can't chain generations. The cooldown needed a new `attempted` flag on the IPC response to distinguish "the model actually ran" from "the cheap trigger filter rejected it" — without it the cooldown would either never engage or would fire on every keystroke in an ineligible file.

  **Honest limitation — not fixed, and it bounds what these fixes can achieve:** these changes make generations *rare*, they do not make an individual generation cheap. One generation still occupies the main process and will still be perceptible. The structural fix is moving inference off the main process (utility process / worker), which is a real architectural change and out of scope tonight. Log this if lag is still noticeable at a lower frequency — the answer then is process isolation, not more tuning.

  **Also found and fixed while editing:** the provider file had been written with two raw NUL bytes embedded in a template literal (`grep` reported it as a binary file), from control characters that survived into the source rather than the intended `\u0000` escape. Replaced with proper escapes; all new files re-verified as LF, no BOM, no NUL. Worth noting as a hazard of generated multi-line file writes on this project.

  Verified: both tsconfigs typecheck clean, `scripts/test-code-inference.mjs` still 29/29. **No runtime testing — the lag fix is unverified until Andre types in a real fresh file.**

- **[2026-08-06]** Code Inference duplicate-on-accept bug fixed. Repro: typed `<!Doc`+`type` in a fresh `.html` file, ghost text appeared, pressed Tab, got `<!Doctype<!DOCTYPE html>`.

  **Cause:** the model restates the code it was given before continuing, and it NORMALIZES while restating — the student's `<!Doctype` came back as canonical `<!DOCTYPE`. `stripPrefixEcho()` compared **case-sensitively**, so `'<!Doctype'.endsWith('<!DOCTYPE')` was false, the echo survived every trim pass, and Monaco inserted the whole thing at the cursor. The range was never wrong: a zero-width range at the cursor is correct, and the completion TEXT was what carried the duplicate.

  **Why the fix is text-trimming and not a wider range — this rules out the obvious alternative.** The instinctive fix is to extend the range back over `<!Doctype` and replace it with canonical `<!DOCTYPE html>`. **That would have silently broken the feature.** Monaco ghost text can only express a pure INSERTION: `computeGhostText()` (`monaco-editor@0.55.1`, `model/computeGhostText.js:70-72`) bails with `if (c.originalLength > 0) return undefined` the instant a suggestion would modify or replace characters already in the buffer. A replacing range renders **no ghost text at all** rather than a corrected suggestion. So the echo is detected case-insensitively but stripped case-PRESERVINGLY, and only the genuinely new tail is inserted.

  **Consequence worth knowing:** accepting now yields `<!Doctype html>` — the student's original casing, not canonical `<!DOCTYPE html>`. That is the correct and only renderable outcome, and it is valid: HTML doctypes are case-insensitive. Code Inference structurally cannot fix casing a student already typed; that is a property of Monaco's ghost text, not a gap in this implementation.

  Also made `stripSuffixOverlap()` case-insensitive — identical bug class on the other side of the cursor, just rarer because the suffix is usually empty in near-empty files. Added `MIN_PREFIX_ECHO = 2` so a single coincidental shared character (a real continuation that happens to start with the letter the prefix ends on) is not mistaken for an echo and eaten.

  **Delete-lag question (asked alongside this): same root cause, not a new bug — and already fixed.** Confirmed in `inlineCompletionsModel.js:226` that Monaco fires `InlineCompletionTriggerKind.Automatic` on any `textChange` with no deletion-specific gating, so backspace re-triggers the provider exactly like typing. It felt worse than typing for a concrete reason: the pre-fix guard order called `model.getValue()` — a full-buffer JS string build — on every keystroke *before* the size check, so deleting through a large garbage buffer paid that cost per backspace. The O(1) reordering (`getLineCount()`/`getValueLength()` first) in the typing-lag fix already removed it.

  **Verified:** `scripts/test-code-inference.mjs` now 35/35, including Andre's exact repro asserted as `prefix + completion` (the duplication is only visible in the joined document, not in the completion alone). Confirmed the new tests genuinely catch the bug by reverting the fix — 4 fail, then pass again once restored. **Still no runtime testing; unverified until Andre accepts a real suggestion.**

- **[2026-08-07]** **PIVOT: Code Inference moved from automatic Monaco ghost text to a confirmation-based flow.** The three entries immediately above (build, typing-lag fix, duplicate-on-accept fix) are the history this replaces.
